# 8. ビット演算とハードウェアレジスタ

> **この章で分かること**
>
> - ビットを立てる／下ろす／調べるイディオムが即書ける
> - `volatile` がなぜ必要かを説明できる
> - DS の色（BGR555）とキー入力をビットで扱える

DS のハードウェアは、**ほぼすべてが「レジスタの中のビット」で制御されます。**
画面モード、スプライトの設定、キー入力、割り込み、DMA、全部です。
この章は DS 開発の実務に直結します。

---

## 8.1 演算子一覧

| 演算子 | 名前 | 例（8bit で表記） |
| --- | --- | --- |
| `&` | AND | `0b1100 & 0b1010` = `0b1000` |
| `\|` | OR | `0b1100 \| 0b1010` = `0b1110` |
| `^` | XOR | `0b1100 ^ 0b1010` = `0b0110` |
| `~` | NOT（ビット反転） | `~0b00001100` = `0b11110011` |
| `<<` | 左シフト | `0b0011 << 2` = `0b1100` |
| `>>` | 右シフト | `0b1100 >> 2` = `0b0011` |

論理演算子 `&&` `||` `!` とは**別物**です。混同しないでください。

```c
if (a & b)    // ビット AND の結果が 0 でないか
if (a && b)   // a も b も 0 でないか
```

### シフトは 2 のべき乗の掛け算・割り算

```c
x << 3     // x * 8
x >> 3     // x / 8（符号なしの場合）
```

ARM9 には整数除算命令が無いので、**2 のべき乗で割るならシフトが圧倒的に速い**です。
座標を「サブピクセル」で持つときにも使います（9 章）。

> **注意:** 型の幅以上のシフト（`u32` を 32 以上）は未定義動作です。
> ビット操作は符号なし（`u32`）で行うのが安全です。

## 8.2 4 つの基本イディオム

これだけは反射で書けるようにしてください。

```c
u32 flags = 0;

flags |=  (1 << 3);       // ① ビット 3 を立てる（セット）
flags &= ~(1 << 3);       // ② ビット 3 を下ろす（クリア）
flags ^=  (1 << 3);       // ③ ビット 3 を反転（トグル）
if (flags & (1 << 3))     // ④ ビット 3 が立っているか（テスト）
```

図で確認します。ビット 3 をクリアする場合:

```
        flags   =  1 0 1 1 1 0 1 1
      (1 << 3)  =  0 0 0 0 1 0 0 0
     ~(1 << 3)  =  1 1 1 1 0 1 1 1
     ────────────────────────────── AND
       結果      =  1 0 1 1 0 0 1 1      ← ビット3だけが 0 になり、他は不変
```

**「クリアには `&= ~`」がポイント**です。`&= (1 << 3)` と書くと他が全部消えます。

### libnds の `BIT()` マクロ

libnds は `nds/ndstypes.h` でこう定義しています。

```c
#define BIT(n) (1u << (n))
```

DS のコードではこちらの表記が主流です。

```c
flags |=  BIT(3);
flags &= ~BIT(3);
if (flags & BIT(3)) { ... }
```

## 8.3 マスクと複数ビットの操作

隣接した複数ビットをひとまとまりの「フィールド」として使うことがあります。

```
   bit:  7  6  5  4  3  2  1  0
       ┌──┬──┬──┬──┬──┬──┬──┬──┐
       │ prio │  color index    │
       └──┴──┴──┴──┴──┴──┴──┴──┘
         6-7          0-5
```

### 取り出す（抽出）

```c
u8 value = 0xB7;                      // 0b10110111

u8 colorIndex = value & 0x3F;         // 下位 6bit → 0b110111 = 55
u8 priority   = (value >> 6) & 0x03;  // 上位 2bit → 0b10 = 2
```

**「右にずらしてからマスク」** が定型です。

> **（発展）** 逆に埋め込むときは、いったんクリアしてから OR します。
> `value = (value & ~0xC0) | ((prio & 0x03) << 6);`

## 8.4 優先順位の罠

**ビット演算子の優先順位は、比較演算子より低いです。** これは C の設計ミスとして有名です。

```c
if (flags & BIT(3) == 0)      // ❌ BIT(3) == 0 が先に評価される → 常に flags & 0 → 0
if ((flags & BIT(3)) == 0)    // ✅ 括弧が必要
```

```c
if (a & b || c)               // (a & b) || c と解釈される（これは意図通りのことが多い）
if (x << 1 + 2)               // x << (1 + 2) と解釈される。+ の方が優先度が高い
```

**ビット演算を書いたら、とりあえず括弧で囲む。** これで事故は防げます。
`-Wall` でも `-Wparentheses` として警告が出ることがあります。

## 8.5 DS のキー入力

キー入力は 1 つの `u32` の中の各ビットに割り当てられています。

```c
scanKeys();                    // 【必須】毎フレーム 1 回だけ呼ぶ

u32 held = keysHeld();         // 今押されているキー
u32 down = keysDown();         // このフレームで押された瞬間
u32 up   = keysUp();           // このフレームで離された瞬間
```

libnds のキー定数（抜粋）:

```c
KEY_A, KEY_B, KEY_X, KEY_Y
KEY_L, KEY_R
KEY_UP, KEY_DOWN, KEY_LEFT, KEY_RIGHT
KEY_START, KEY_SELECT
KEY_TOUCH       // タッチスクリーンが押されている
KEY_LID         // 本体が閉じられた
```

使い方:

```c
scanKeys();
u32 keys = keysHeld();

if (keys & KEY_LEFT)  player.x -= 2;      // 押しっぱなしで動く
if (keys & KEY_RIGHT) player.x += 2;

if (keysDown() & KEY_A) {                  // 押した瞬間だけ 1 回
    shootBullet();
}

// 複数キーの同時判定
if ((keys & (KEY_L | KEY_R)) == (KEY_L | KEY_R)) {
    // L と R が両方押されている
}

// どちらかが押されている
if (keys & (KEY_L | KEY_R)) { ... }
```

`held` と `down` の使い分けが重要です。
移動は `held`（押しっぱなしで動き続ける）、
ジャンプや決定は `down`（1 回だけ反応する）、と覚えてください。

## 8.6 DS の色 — BGR555

DS の色は **16bit に 5bit ずつの BGR + 1bit のアルファ**で表現されます。

```
   bit: 15   14        10  9         5  4         0
       ┌───┬─────────────┬─────────────┬─────────────┐
       │ A │   Blue (5)  │  Green (5)  │   Red (5)   │
       └───┴─────────────┴─────────────┴─────────────┘
```

各成分は **0〜31**（PC の 0〜255 ではない）です。

libnds のマクロ:

```c
#define RGB15(r, g, b)      ((r) | ((g) << 5) | ((b) << 10))
#define ARGB16(a, r, g, b)  (((a) << 15) | (r) | ((g) << 5) | ((b) << 10))
#define RGB8(r, g, b)       (((r) >> 3) | (((g) >> 3) << 5) | (((b) >> 3) << 10))
```

自分で書いてみると理解が深まります。

```c
static inline u16 myRGB15(int r, int g, int b)
{
    return (u16)((r & 31) | ((g & 31) << 5) | ((b & 31) << 10));
}

u16 red    = myRGB15(31,  0,  0);
u16 white  = myRGB15(31, 31, 31);
u16 purple = myRGB15(20,  0, 20);
```

分解する（アンパック）:

```c
static inline int getRed(u16 c)   { return  c        & 31; }
static inline int getGreen(u16 c) { return (c >>  5) & 31; }
static inline int getBlue(u16 c)  { return (c >> 10) & 31; }
```

PC の 8bit カラー（0〜255）から変換するには 3bit 右シフトして 0〜31 に落とします。
libnds の `RGB8` がまさにこれをやっています。

```c
u16 c = RGB8(255, 128, 0);      // = myRGB15(31, 16, 0)
```

パレットへの書き込みはこうなります。

```c
BG_PALETTE[1] = RGB15(31, 0, 0);      // 背景パレットの色 1 を赤に
SPRITE_PALETTE[1] = RGB15(0, 31, 0);  // スプライトパレットの色 1 を緑に
```

## 8.7 ハードウェアレジスタと `volatile`

### メモリマップド I/O

DS のハードウェア制御は、**特定のアドレスへの読み書き**で行います。
CPU からは普通のメモリに見えますが、その先にはハードウェアがつながっています。

libnds の定義（`nds/arm9/math.h` より実物）:

```c
#define REG_DIVCNT      (*(vu16 *)(0x04000280))
#define REG_DIV_NUMER   (*(vs64 *)(0x04000290))
#define REG_DIV_DENOM   (*(vs64 *)(0x04000298))
#define REG_DIV_RESULT  (*(vs64 *)(0x040002A0))
```

`vu16` は `volatile uint16_t`、`vs64` は `volatile int64_t` です（4 章参照）。

### `volatile` が無いと何が起こるか

コンパイラは「メモリの中身はプログラムが書き換えない限り変わらない」と仮定して最適化します。

```c
// volatile が無いと仮定した場合
u16 *reg = (u16 *)0x04000280;

*reg = 0x0001;          // コンパイラ: 「この書き込みは誰も読まないから消そう」
*reg = 0x0002;          // ← 前の書き込みが消えると、ハードウェアへの指示が届かない

while (*reg & 0x8000) { }   // コンパイラ:「reg は変わらないから 1 回読めば十分」
                            // ← 無限ループになる
```

`volatile` を付けると、コンパイラは
**「このアクセスは省略も並べ替えもキャッシュもするな。書いた通りに実行しろ」**
と指示されたことになります。

```c
#define REG_DIVCNT (*(vu16 *)(0x04000280))

REG_DIVCNT = DIV_32_32;
while (REG_DIVCNT & DIV_BUSY) { }    // 毎回ちゃんと読みに行く
```

**ルール: ハードウェアレジスタと、割り込みハンドラから書き換えられる変数には `volatile` を付ける。**
それ以外の普通の変数には付けないでください（最適化を妨げるだけです）。

### 割り込みと共有する変数

割り込みハンドラから書き換えられる変数にも `volatile` が要ります。
付けないと、メインループ側が「変わらないはず」と判断して無限ループになります。

```c
static volatile int sVBlankCount = 0;   // volatile が必要
```

## 確認問題

**Q1.** `flags` のビット 5 を立て、ビット 2 を下ろすコードを書いてください。

<details><summary>解答</summary>

```c
flags |=  BIT(5);       // または flags |=  (1u << 5);
flags &= ~BIT(2);       // または flags &= ~(1u << 2);
```

クリアは `&= ~` であることに注意。`&= BIT(2)` と書くと他のビットが全部消えます。
</details>

**Q2.** 次のコードが期待通り動かない理由を説明し、修正してください。

```c
if (keysHeld() & KEY_A == 0) {
    // A が押されていないときの処理
}
```

<details><summary>解答</summary>

**演算子の優先順位**の問題です。`==` は `&` より優先順位が高いので、
`keysHeld() & (KEY_A == 0)` と解釈されます。

`KEY_A` は 0 ではない定数なので `KEY_A == 0` は `0`。
つまり `keysHeld() & 0` = 常に 0 = 偽となり、**このブロックには絶対に入りません**。

修正:

```c
if ((keysHeld() & KEY_A) == 0) { ... }
// または
if (!(keysHeld() & KEY_A)) { ... }
```

**ビット演算は括弧で囲む**、を習慣にしてください。
</details>

**Q3.** DS の色は 16bit の BGR555 です。R=31, G=15, B=0 の色を表す `u16` の値を、
16 進数で求めてください。

<details><summary>解答</summary>

```
R = 31 = 0b11111  → bit 0-4
G = 15 = 0b01111  → bit 5-9
B =  0 = 0b00000  → bit 10-14
A =  0            → bit 15

値 = 31 | (15 << 5) | (0 << 10)
   = 0x1F | 0x1E0
   = 0x01FF
```

ビット列: `0 00000 01111 11111` = `0x01FF`

コードでは `RGB15(31, 15, 0)` と書けば同じ値になります。
（アルファビットを立てるなら `ARGB16(1, 31, 15, 0)` = `0x81FF`）
</details>
