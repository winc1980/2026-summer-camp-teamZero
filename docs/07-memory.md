# 7. メモリ管理

> **この章で分かること**
>
> - DS のメモリ地図を頭に入れる
> - 変数の「3 つの寿命」を区別できる
> - スタックに大きな配列を置いてはいけない理由が分かる
> - DS における `malloc` の作法を身につける

---

## 7.1 DS のメモリ地図

まず、自分が何と戦っているかを知りましょう。

| 領域 | アドレス | サイズ | 用途 |
| --- | --- | --- | --- |
| **メインRAM (EWRAM)** | `0x02000000` | **4 MB**（DSi は 16 MB） | コード・データ・ヒープ。主戦場 |
| ITCM | `0x01000000` | 32 KB | ARM9 命令キャッシュ相当。超高速コード置き場 |
| DTCM | `0x0B000000` | 16 KB | ARM9 データ用の超高速領域。**スタックがここ** |
| 共有WRAM | `0x03000000` | 32 KB | ARM9/ARM7 間の通信 |
| ARM7 WRAM | `0x03800000` | 64 KB | ARM7 専用 |
| VRAM (A〜I) | `0x06000000`〜 | 合計 656 KB | 画面・スプライト・テクスチャ |
| パレット | `0x05000000` | 2 KB | 色 |
| OAM | `0x07000000` | 2 KB | スプライト属性（128 個ぶん） |

比較のために: スマホのアプリが数百 MB のメモリを平気で使う世界に対し、
**DS のメインメモリは 4 MB です。** 画像 1 枚をうっかり非圧縮で持つだけで破綻します。

そして最も重要な数字がこれです。

> **ARM9 のスタックは DTCM（16 KB）の中にあります。**

つまり、ローカル変数として置けるデータの総量は **数 KB オーダー** です。

## 7.2 変数の 3 つの寿命

C の変数は、**どこに置かれ、いつ消えるか**で 3 種類に分かれます。
これを意識せずに C を書くことはできません。

```c
int   gGlobal    = 1;        // ① 静的記憶域（プログラム終了まで生きる）

void f(void)
{
    int          local  = 2; // ② 自動記憶域（スタック。関数を抜けると消える）
    static int   keep   = 3; // ① 静的記憶域（名前はローカルだが寿命はプログラム全体）
    int         *heap   = malloc(100);  // ③ 動的記憶域（free するまで生きる）

    free(heap);
}
```

### ① 静的記憶域 — グローバル変数と `static`

| 特徴 | |
| --- | --- |
| 置かれる場所 | `.data`（初期値あり） / `.bss`（初期値 0） |
| 寿命 | プログラムの最初から最後まで |
| 初期化 | **明示しなければ 0 で初期化される（保証あり）** |
| サイズ | ビルド時に確定。ROM/RAM 使用量に直結 |

```c
int   gScore;                 // 0 に初期化される（.bss）
Enemy gEnemies[64];           // 全部 0（.bss）
const char gTitle[] = "GAME"; // 初期値あり（.data / .rodata）
```

**DS では静的記憶域が主役です。**
サイズが起動時に確定するので、「実行中にメモリが足りなくなる」ことがありません。
敵の配列も、マップも、作業バッファも、静的に取ってしまうのが一番安全です。

### ② 自動記憶域（スタック）

| 特徴 | |
| --- | --- |
| 置かれる場所 | スタック（DS の ARM9 では DTCM 内、16 KB 程度） |
| 寿命 | ブロック（`{}`）を抜けるまで |
| 初期化 | **されない。中身は前に使われたゴミ** |
| サイズ | **絶対に大きくしないこと** |

```c
void f(void)
{
    int x;               // 未初期化。中身は不定
    printf("%d\n", x);   // 未定義動作。ゴミが出る
}
```

**「ローカル変数は 0 で初期化されない」** は他言語から来ると必ず一度は踏みます。
宣言と同時に初期化する習慣を付けてください。

```c
int x = 0;
Player p = {0};
```

### ③ 動的記憶域（ヒープ）

| 特徴 | |
| --- | --- |
| 置かれる場所 | メインRAM の空き領域 |
| 寿命 | `free` するまで |
| 初期化 | `malloc` はされない、`calloc` は 0 |
| サイズ | 実行時に決められる |

## 7.3 【重要】スタックに大きな配列を置かない

これが DS 開発で最初にハマる罠です。

```c
void loadStage(void)
{
    u8 buffer[64 * 1024];      // 64 KB！ スタックは 16 KB しかない
    ...
}
```

PC ならスタックは 8 MB あるので通ってしまいます。**DS では即座に壊れます。**

しかも、**スタックオーバーフローを検出する仕組みがありません。**
スタックが DTCM の端を突き抜けて、隣のデータを静かに上書きし、
まったく無関係な場所で挙動がおかしくなります。デバッグは地獄です。

### 目安

| サイズ | 判断 |
| --- | --- |
| 数十バイト〜数百バイト | ローカル変数で OK |
| 1 KB 程度 | 慎重に。ネストが深くないなら許容 |
| **数 KB 以上** | **絶対にローカルにしない** |

### 対処法

```c
// (a) static にする → 静的記憶域に移動する
void loadStage(void)
{
    static u8 buffer[64 * 1024];    // .bss に置かれる
    ...
}

// (b) ファイルスコープの static にする（複数関数で共有するなら）
static u8 sStageBuffer[64 * 1024];

// (c) malloc する（サイズが実行時に決まるなら）
void loadStage(int size)
{
    u8 *buffer = malloc(size);
    if (!buffer) return;
    ...
    free(buffer);
}
```

`static` にすると**関数の再入や再帰ができなくなる**（同じバッファを共有するため）ので、
そこだけ注意してください。ゲームループから 1 箇所で呼ぶ処理なら問題ありません。

構造体も同じです。

```c
void f(void)
{
    Enemy allEnemies[256];     // Enemy が 32 バイトなら 8 KB。危ない
}
```

## 7.4 `malloc` と `free`

```c
#include <stdlib.h>

u16 *buf = malloc(256 * sizeof(u16));   // 512 バイト確保
if (buf == NULL) {                      // 【必須】失敗チェック
    // メモリ不足。ここで諦めるか、別の手を打つ
    return;
}

buf[0] = 0x1234;

free(buf);                              // 使い終わったら返す
buf = NULL;                             // 【推奨】ダングリング防止
```

| 関数 | 動作 |
| --- | --- |
| `malloc(n)` | n バイト確保。**中身は不定** |
| `calloc(count, size)` | `count * size` バイト確保。**0 で初期化される** |
| `realloc(p, n)` | サイズ変更。**アドレスが変わりうる**（戻り値を必ず受ける） |
| `free(p)` | 解放。`free(NULL)` は安全（何もしない） |

### `sizeof` を使って書く

```c
u16 *buf = malloc(256 * sizeof(u16));       // 良い
u16 *buf = malloc(256 * 2);                 // 型を変えたときに壊れる
Enemy *e = malloc(sizeof(Enemy) * count);   // 良い
Enemy *e = malloc(sizeof(*e) * count);      // さらに良い（型名を書かない）
```

## 7.5 DS での `malloc` の作法

**結論から言うと、合宿では `malloc` をほとんど使わない方向で設計してください。**

理由:

1. **メモリが 4 MB しかない。** 何をどれだけ使っているかを把握しきれなくなる
2. **フラグメンテーション（断片化）。**
   確保と解放を繰り返すと、合計の空きは足りているのに連続領域が取れなくなる。
   ゲームループの中で毎フレーム確保/解放していると、20 分プレイしたあたりで確保に失敗する、
   といった再現困難なバグになります
3. **失敗したときに何もできない。** PC ならスワップがありますが、DS には無い

### 推奨する設計方針

```
起動時         : 必要なものを全部確保する（または最初から static で取る）
ゲームループ中 : 一切 malloc / free しない
ステージ切替時 : まとめて解放し、まとめて確保し直す（許容範囲）
```

具体的には:

```c
// ✅ 個数の上限を決めて静的に取る
#define MAX_ENEMIES 32
static Enemy sEnemies[MAX_ENEMIES];

// ✅ 起動時に一度だけ確保する
static u16 *sTileBuffer = NULL;

void gameInit(void)
{
    sTileBuffer = malloc(TILE_BUFFER_SIZE);
    if (!sTileBuffer) {
        consoleDemoInit();
        printf("out of memory\n");
        while (1) swiWaitForVBlank();
    }
}

// ❌ 毎フレーム確保する
void updateBullets(void)
{
    Bullet *tmp = malloc(sizeof(Bullet) * count);   // やめる
    ...
    free(tmp);
}
```

「上限を決めて固定配列で持つ」のは手抜きに見えるかもしれませんが、
**組み込みやゲーム機の世界では標準的な設計判断です。**
「弾は最大 64 発まで」という制約は、ゲームデザインとしても大抵問題になりません。

## 7.6 メモリ関連のバグ 4 種

DS 開発で遭遇するのはだいたいこの 4 つです。

### (a) バッファオーバーフロー

```c
u8 buf[10];
for (int i = 0; i <= 10; i++) buf[i] = 0;   // i == 10 で 1 バイトはみ出す
```

`<=` と `<` の取り違えが典型。**隣の変数が壊れます。**

### (b) 未初期化の読み取り

```c
Player p;              // 中身はゴミ
if (p.hp > 0) { ... }  // 何が起きるか分からない
```

→ `Player p = {0};` と書く。

### (c) ダングリングポインタ（解放後／スコープ外）

```c
free(buf);
buf[0] = 1;            // use-after-free
```

→ `free` の直後に `buf = NULL;`。

### (d) スタックオーバーフロー

7.3 の通り。**検出されないのが最悪の性質です。**

### 共通の対策

```c
// ヒープを使うなら、確保と解放を対にして同じ関数内に書く
void doSomething(void)
{
    u8 *buf = malloc(SIZE);
    if (!buf) return;

    ...

    free(buf);
}
```

そして**そもそも malloc を使わない**のが一番の対策です（7.5）。

## 確認問題

**Q1.** 次のコードの問題点を指摘してください。

```c
void decompressStage(void)
{
    u8 work[32 * 1024];
    ...
}
```

<details><summary>解答</summary>

32 KB のローカル配列はスタックに置かれますが、
DS の ARM9 のスタックは DTCM（16 KB）内にあるため、**スタックを溢れさせます**。

しかも C にはスタックオーバーフローの検出機構が無いので、
エラーにならずに隣のメモリを静かに破壊し、無関係な場所で不具合が出ます。

修正:

```c
void decompressStage(void)
{
    static u8 work[32 * 1024];      // .bss に置く
    ...
}
```

（再帰・再入しない前提。する可能性があるなら `malloc` を使います）
</details>

**Q2.** 次の 2 つの変数の違いを、置かれる場所・寿命・初期化の 3 点で述べてください。

```c
void f(void)
{
    int a = 0;
    static int b = 0;
}
```

<details><summary>解答</summary>

| | `a` | `b` |
| --- | --- | --- |
| 場所 | スタック（DS では DTCM 内） | 静的記憶域（`.bss` / `.data`） |
| 寿命 | `f` を抜けると消える。呼ぶたびに作り直される | プログラム全体。値が次回呼び出しにも残る |
| 初期化 | 呼ばれるたびに 0 が代入される | プログラム起動時に 1 回だけ 0 になる |

</details>

**Q3.** DS のゲームループの中で `malloc` / `free` を繰り返すのが危険なのはなぜですか。

<details><summary>解答</summary>

**フラグメンテーション（断片化）**が進むためです。
確保と解放を繰り返すと空き領域が細切れになり、
合計の空きバイト数は足りているのに、必要なサイズの**連続領域**が取れなくなります。

DS はメモリが 4 MB しかなく、仮想メモリもスワップも無いため、
これが「しばらくプレイしていると突然確保に失敗する」という、
再現が難しく発生タイミングも読めないバグになります。

対策: 上限を決めた固定配列（オブジェクトプール）で管理し、
確保は起動時かステージ切替時にまとめて行う。
</details>
